# 設計方針と制約

## raylibらしい小ささ

RTextJPは、C言語の構造体と関数だけで扱えること、所有権を隠さないこと、ビルドシステムを強制しない
ことを優先しています。クラス、例外、暗黙のグローバル状態はありません。

シングルヘッダは宣言部と実装部に分かれます。`RTEXTJP_IMPLEMENTATION` を1回定義する方式はraylib周辺の
小さなライブラリと同じです。内部だけで使う補助関数は `static`、公開関数は標準では外部リンケージ、
`RTEXTJP_STATIC` 指定時は公開関数も `static` になります。

## UTF-8を境界にする

公開文字列はすべてNUL終端UTF-8です。OSのワイド文字型やロケール依存のマルチバイト関数は公開APIへ
持ち込みません。不正なバイト列を読む関数は1バイトずつU+FFFDへ置き換えて必ず前進します。

文字位置を扱う入力欄の内部値はバイト位置です。ただし移動、削除、切り詰めはUTF-8境界でのみ行い、
継続バイトの途中を指さないようにします。

## フォントアトラスは明示的に小さくする

CJK統合漢字全体は2万字以上あります。すべてを1枚のテクスチャへ自動で入れると、起動時間、メモリ、
GPU上限の問題が初心者にも発生します。そのため初版では、アプリが使う文字列を明示して読み込む方式を
標準にしました。

固定文を列挙できない入力画面向けに、JIS X 0208のかな・非漢字・第1水準・第2水準プリセットも
選べます。プリセットはUnicodeコードポイントの静的な表で、実行時の文字コード変換やロケールには
依存しません。第1水準2,965字、第2水準3,390字、非漢字524字の件数は生成時と自動テストで確認します。

このプリセットは収録範囲をフォントへ要求する機能であり、フォントにない字形を生成する機能では
ありません。また、公開文字列の境界は常にUTF-8です。JISプリセットを選んでもShift_JISやEUC-JPの
バイト列を直接受け取るわけではありません。

将来の候補には、複数ページの動的グリフキャッシュと文字集合ファイルの読み込みがあります。
これらは所有権とアトラス更新の複雑さが増すため、現在は含めていません。

## レイアウト

横書きは追加メモリなしの2段階処理です。最初に行幅と全体高を測定し、次に同じ規則で描画します。
これにより中央・下揃えでも行配列を確保しません。

折り返し候補は次の優先順位です。

1. 明示的な改行
2. 英語などの空白
3. CJK文字の境界
4. 幅より長い単語の強制分割

禁則対象の境界は候補から外します。ほかに候補がない場合、句読点1個程度が幅を越えることを許して
行頭禁則を優先する場合があります。

## 縦書きの範囲

縦書きはゲームの手紙、掛け軸、演出テキストを軽量に作るためのマス目配置です。フォントの
`vert` / `vrt2` OpenType機能は適用しません。そのため括弧・句読点の専用字形、長音の回転、
ラテン文字の回転は本格的な縦組みと異なります。この制約はAPIコメントにも明記しています。

## スレッドと描画状態

UTF-8補助と入力バッファ操作は、別々の状態を渡す限りグローバルな可変状態を持ちません。
フォント読み込みと描画はraylibの制約に従い、通常はメインスレッドで行います。

`clip = true` の描画関数は `BeginScissorMode()` と `EndScissorMode()` を対で呼びます。raylibの
シザー状態を外側で管理している場合は `clip = false` にしてください。
